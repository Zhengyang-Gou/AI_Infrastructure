# 01 · Scheduler

理解调度器如何在每轮执行中选择请求、分配 Token 和缓存资源，并在资源不足时让请求暂停、恢复。

**阅读范围：** 从 vLLM V1 的设计思路出发，以普通文本生成、同步执行、Prefill 与 Decode 在同一实例中的场景理解机制。异步调度、推测解码、多模态和分布式 KV 传输留到后续学习。第 4 节补充 PD 分离架构下的区别。

## 本篇在做什么

```text
新请求 --> 等待队列：等待获准执行
               |
               v
开始本轮调度
    |
    v
先检查已接纳请求：还需要计算多少 Token？
    |
    v
检查 Token 预算与 KV Cache 容量
    +-- KV 不足 --> 抢占请求，释放缓存引用，放回等待队列
    |
    v
有剩余预算与请求名额时，尝试接纳等待队列中的请求
    |
    v
执行计划：选中请求、本轮计算量、缓存使用安排
    |
    v
执行器：组织输入，运行模型，取得输出
    |
    v
更新请求的生成结果与停止状态
    +-- 未完成 --> 留在系统中，等待下一轮调度
    |
    +-- 已完成 --> 移出队列，释放缓存引用
```

**读图说明：** Scheduler 决定“这一轮让谁算、算多少”，执行器负责把计划变成模型计算。一次调度只推进请求的一部分工作，不必等一个请求全部生成完成后再处理下一个。这里采用先安排已接纳请求、再尝试接纳等待请求的策略。发生抢占时，可以暂缓接纳新请求，优先缓解已有请求的缓存压力。

## 1 · 请求生命周期与队列

一个请求需要跨越多轮执行，因此调度器必须保存它的 Token、计算进度和生命周期状态。

```text
新请求到达 --> 等待接纳 --> 活跃请求
                           |
                           +-- 分块 Prefill 或 Decode --> 下一轮继续
                           |
                           +-- 缓存不足，被抢占 --> 暂停并等待恢复
                           |                         |
                           |                         +--> 重新获准执行
                           |
                           +-- 达到停止条件或被取消 --> 结束并释放资源
```

**读图说明：** 请求的生命周期与计算阶段是两个维度。“活跃”表示已经获准使用执行资源，Prefill / Decode 表示正在做什么计算。长 Prompt 获准执行后，即使尚未完成 Prefill，也可以属于活跃请求。

| 概念 | 含义 |
| --- | --- |
| 等待请求 | 尚未获准执行，或被抢占后等待恢复的请求 |
| 活跃请求 | 已获准执行、尚未结束，可能处于 Prefill 或 Decode |
| 本轮选中请求 | 实际安排了当前一轮计算的请求 |
| 结束请求 | 已停止、达到长度限制或被取消，进入资源清理阶段 |

活跃请求不一定每轮都参与计算。是否获得本轮执行机会，还取决于计算预算、缓存容量和依赖是否就绪。

## 2 · 调度粒度与 Token 进度

调度以一次模型执行迭代为单位。对一条请求，需要区分“已经有的 Token”和“已经算过的 Token”：采样得到一个新 Token 后，它的 KV 通常要在下一次前向中计算。

可以把请求的工作量分成三部分：

| 进度 | 含义 |
| --- | --- |
| 已有 Token | Prompt 与已经生成的输出 Token |
| 可复用的计算进度 | 已有有效 KV、能直接作为上下文使用的部分 |
| 待计算 Token | 已经存在，但尚需前向计算才能建立 KV 的部分 |

```text
待计算量 = 已有 Token 数 − 可复用的计算进度
本轮计算量 ≤ 待计算量，且不能超过剩余 Token 预算
```

这种表示将 Prefill 和 Decode 统一为“还有多少 Token 需要计算”。Prefill 通常有多个 Prompt Token 尚未处理；普通 Decode 通常只需要处理最新生成的一个 Token。

以 6 个 Prompt Token 为例，假设每轮最多给这条请求安排 4 个 Token：

| 时刻 | 已有 Token 数 | 已计算 Token 数 | 待计算量 | 本轮行为 |
| --- | --- | --- | --- | --- |
| 初始 | 6 | 0 | 6 | 计算前 4 个 Prompt Token |
| 第一轮后 | 6 | 4 | 2 | 计算剩余 2 个 Prompt Token，采样首个输出 Token |
| 第二轮后 | 7 | 6 | 1 | 计算刚生成的 Token，采样下一个 Token |
| 第三轮后 | 8 | 7 | 1 | 继续 Decode |

**读表说明：** 中间 Prefill 分块只推进计算进度；Prompt 处理完成后，才开始得到正式输出 Token。生成一个新 Token，并不意味着它自己的 KV 已经计算完成。

统一计算进度后，调度器可以用同一种方式分配两阶段的工作，而不必把请求简单地分成两个互不相通的批次。这里的进度指已经可用的上下文；异步执行时，还需要区分“已安排计算”和“结果已就绪”。

## 3 · 资源预算与请求准入

选择请求时，需要同时满足三类主要约束。

| 约束 | 限制什么 | 不满足时怎么办 |
| --- | --- | --- |
| Token 预算 | 本轮能安排的输入 Token 总量 | 分块处理，或留到下一轮 |
| 请求数上限 | 能同时处理的请求数量 | 暂缓接纳新的等待请求 |
| KV Cache 容量 | 保存请求上下文所需的缓存块 | 等待资源释放，或抢占已有请求 |

每安排一条请求，就从本轮剩余 Token 预算中扣除对应计算量。接纳新请求时，还要确认有并发名额，并且能够为它建立和保留所需 KV。只有这些条件同时满足，请求才能获得执行机会。

需要区分：**Token 预算每轮重新取得，KV Cache 会跨轮次保留。** 一条 Decode 请求本轮可能只计算一个 Token，却仍然需要保存很长的上下文 KV。因此，Token 预算还有剩余时，也可能因缓存不足而无法接纳新请求。KV 准入检查还可能考虑完整输入的容量需求，而不只检查当前分块。

Prefix Cache 命中时，可复用前缀减少需要重新计算的 Token；Scheduler 根据命中进度安排剩余工作。前缀识别和缓存块管理在后续章节展开。

## 4 · 请求选择与 Prefill / Decode 协作

调度策略需要回答两个问题：等待请求按什么顺序选，以及已有请求与新请求如何共享一轮执行。

| 决策 | 基本机制 |
| --- | --- |
| 等待请求排序 | FCFS 按到达顺序；Priority 按优先级选择，同优先级再看到达时间 |
| 已有请求与新请求 | 先安排已接纳请求，再利用剩余资源接纳等待请求 |
| 长 Prompt 的处理 | 开启 Chunked Prefill 后，将尚未计算的 Prompt 分多轮处理 |
| 批次组成 | 同一轮可以包含 Decode 请求和 Prefill 分块 |

```text
本轮 Token 预算：8
    |
    +-- A：Decode，分配 1 个 Token
    +-- B：Decode，分配 1 个 Token
    +-- C：长 Prompt 的 Prefill，分配剩余 6 个 Token
    |
    v
一个混合批次：{A: 1, B: 1, C: 6}
```

**读图说明：** 在 Prefill 与 Decode 同实例的场景中，新请求 C 不必一次算完整个 Prompt，可以先计算一段，让 A、B 在这一轮继续输出。这是 Chunked Prefill 与调度器协作形成混合批次的基本方式。

“先处理已接纳请求”不等于“所有 Decode 永远排在所有 Prefill 前面”：已接纳请求中也可能有未完成的 Prefill。FCFS 也不意味着必须等队首请求全部生成完才服务后面的请求，它主要影响选择顺序。

调度大小会影响用户体验：长 Prefill 一次安排较多 Token，有利于推进 Prompt，但可能延长整轮执行时间，让同批次 Decode 的输出间隔变大。分块较小时，可以更频繁地安排 Decode，但长 Prompt 需要更多轮才能完成。学习时重点观察首 Token 延迟（TTFT）、输出 Token 间隔（ITL / TPOT）与整体吞吐之间的取舍。

### 连续批处理与 PD 分离

Continuous Batching 的核心是：**在执行迭代之间动态调整批次成员，结束的请求退出，符合条件的新请求加入。** 它不要求同一批次同时包含 Prefill 和 Decode。

| 概念 | 解决什么问题 |
| --- | --- |
| Continuous Batching | 请求完成时间不同，如何及时移出完成请求并补入新请求 |
| Prefill / Decode 混合批次 | 两种计算共用一个实例时，如何在同一轮分配计算预算 |
| PD 分离 | 将 Prefill 与 Decode 放到不同实例或资源池，减少两种计算之间的干扰 |

在 PD 分离架构中，请求先在 Prefill 实例处理 Prompt，再把 KV 等所需状态交给 Decode 实例继续生成。逐 Token 的连续批处理主要体现在 Decode 侧：已有请求每轮继续推进，完成的请求退出，完成 Prefill 且 KV 就绪的请求加入。

```text
Prefill 侧：处理 C 的 Prompt --> 传输 KV --> C 在 Decode 侧就绪

Decode 第 1 轮：[A, B]       --> A、B 各推进一步
       轮次间：A 结束退出；C 就绪并获准加入
Decode 第 2 轮：[B, C]       --> B、C 各推进一步
```

**读图说明：** 上图 Decode 侧的批次只包含 Decode 工作，仍然可以进行连续批处理。Prefill 侧也需要排队和组批；若采用分块并在迭代之间调整请求，同样可以动态调度。PD 分离改变两阶段的执行位置，连续批处理决定各实例中的请求如何加入和退出批次。参考 [vLLM 官方 PD 分离说明](https://docs.vllm.ai/en/latest/features/disagg_prefill/)。

## 5 · KV 不足时的抢占与恢复

请求生成得越长，所需 KV Cache 也可能继续增加。已有请求准备执行下一轮时，如果无法取得缓存块，调度器可以暂停某条请求，给其他请求腾出空间。

```text
当前请求需要更多 KV 块
    |
    v
分配失败
    |
    v
选择被抢占请求
    |
    v
释放该请求的缓存引用，保留 Prompt 和已生成 Token
    |
    v
重新确认可复用的计算进度，进入等待恢复的队列
    |
    v
资源允许后恢复：用保留的 Token 重建所需 KV
    |
    v
继续生成
```

**读图说明：** 抢占保留请求的文本生成进度，但会使部分计算结果需要重新建立。这里采用重算式恢复：已有 Token 不必重新生成，但它们对应的 KV 可能需要重新计算。启用 Prefix Cache 时，仍可复用可用的缓存前缀。

抢占对象由调度策略决定。例如，按到达顺序服务时，可以优先暂停较晚接纳的请求；采用优先级时，可以优先暂停较低优先级的请求。选择对象时，需要同时考虑资源释放量、重算代价与公平性。

抢占会带来重算成本和额外等待时间。若某个请求反复经历“恢复 → KV 不足 → 再抢占”，即使 GPU 持续执行，实际生成效率也可能下降。理解机制时，要把吞吐与抢占次数、缓存占用一起看。

## 6 · 调度、执行与反馈闭环

调度输出是一份执行计划，包含本轮请求、每条请求的 Token 数，以及执行所需的缓存块信息。

例如，本轮计划可以是：A 处理 1 个 Decode 输入 Token，B 处理 1 个 Decode 输入 Token，C 处理 6 个 Prompt Token。执行器根据各请求的进度组织输入和上下文，模型计算完成后，再把生成结果反馈给调度器。

**本轮处理的输入 Token 数，不等于本轮新生成的输出 Token 数。** C 的 6 个 Token 是 Prompt 的计算工作量；如果 Prompt 尚未处理完，就还不能得到正式输出。

```text
本轮执行结果
    |
    +-- Prefill 分块尚未完成 --> 保留计算进度，下一轮继续
    |
    +-- 可接受生成结果 --> 追加输出 Token
                               |
                               v
                           检查停止条件
                               +-- 未停止 --> 后续轮次继续生成
                               |
                               +-- EOS / 长度限制 / 取消 --> 结束并释放资源
```

**读图说明：** 一轮完成后，请求状态会发生变化；新请求也可能已经到达。下一轮根据这些变化重新决定批次成员和计算量，这为 Continuous Batching 提供了基础。本图按同步执行理解这个反馈闭环；异步执行还需要跟踪尚未完成的工作。

## 手工推演：两个 Decode 与一个长 Prompt

假设 Prefill 与 Decode 在同一实例中执行，A、B 已完成 Prefill，C 刚到达，Prompt 长度为 10。每轮 Token 预算为 8，最多运行 3 个请求，开启 Chunked Prefill，KV 容量足够；不使用 Prefix Cache，也不额外限制单个 Prefill 分块大小。A 在第二轮后结束，B、C 在推演期间继续生成。

| 轮次 | A 的分配 | B 的分配 | C 的分配 | 本轮 Token 总量 | 执行后变化 |
| --- | --- | --- | --- | --- | --- |
| 第 1 轮 | Decode 1 | Decode 1 | Prefill 6 | 8 | C 已获准执行，Prompt 尚余 4 个未计算 |
| 第 2 轮 | Decode 1 | Decode 1 | Prefill 4 | 6 | C 完成 Prefill，得到首个输出 Token；A 结束并释放资源 |
| 第 3 轮 | 已结束 | Decode 1 | Decode 1 | 2 | B、C 继续生成；可用名额允许接纳新的等待请求 |

**读表说明：** 第 1 轮后 C 已经属于活跃请求，却仍在做 Prefill。第 2 轮 C 处理了 4 个输入 Token，但只得到首个输出 Token。没有更多可执行请求时，Token 预算可以剩余，不必填满。

再加入一次缓存不足：假设第 3 轮 B 需要申请新块，分配失败，且调度器选中 C 作为抢占对象。

```text
C：Prompt 10 个 + 首个输出 Token 1 个
    |
    v
被抢占：保留 11 个 Token，释放 KV 引用，计算进度重置
    |
    v
等待资源允许后恢复
    |
    v
没有可复用前缀时，重新计算这 11 个 Token 的 KV
    |
    v
继续采样后续输出
```

**功能描述：** 这次抢占让 C 的已有输出保留下来，但它需要重新构建上下文才能继续。恢复所需轮数取决于当时的 Token 预算和其他请求占用情况。

## 与 Mini Engine 的机制对照

| 机制 | 简化引擎的常见组织方式 | 本篇采用的设计思路 |
| --- | --- | --- |
| 本轮组织方式 | 先选择计算阶段，再为该阶段组批 | 为每条请求分配本轮 Token 计算量 |
| Prefill / Decode 协作 | 一轮处理一种阶段 | 一轮可以包含两种阶段的工作 |
| 长 Prompt 的生命周期 | 可能等 Prefill 完成后才视为活跃请求 | 获准执行后即可跨轮推进分块 Prefill |
| 计算进度 | 分别理解 Prompt 处理和生成步数 | 用可复用上下文与待计算量统一表示 |
| 抢占恢复 | 保留 Token，释放请求占用的缓存，等待重算 | 同样保留文本进度，并重新建立可用上下文 |

两种方式都围绕请求进度、计算预算和缓存容量做决策。统一 Token 进度的意义在于：同一轮可以灵活安排不同阶段、不同计算量的请求，为连续批处理和分块 Prefill 提供共同基础。
