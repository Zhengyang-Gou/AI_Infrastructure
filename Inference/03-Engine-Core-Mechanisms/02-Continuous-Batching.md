# 02 · Continuous Batching

理解请求如何在模型执行迭代之间加入和退出 Batch，以及 PD 分离后，Prefill、KV 传输和 Decode 如何共同维持连续生成。

**阅读范围：** 从 vLLM V1 的设计思路出发，先简述 Prefill / Decode 共用实例的情况，再重点讨论 PD 分离。按普通自回归生成、每条请求每次 Decode 处理一个输入 Token、同步迭代来推演；不展开推测解码、Beam Search、多模态和异步流水线。

前置知识：[Scheduler](01-Scheduler.md)、[Prefill 与 Decode](../01-LLM-Inference-Basics/03-Prefill-and-Decode.md)。

## 1 · 先理解“连续”的含义

LLM 请求的输出长度不同，而且一个请求需要执行多次前向才能完成生成。若一个 Batch 的成员一直固定到所有请求结束，短请求结束后留下的执行容量无法及时交给新请求，新到达的请求也要等待长请求。

**Continuous Batching 的核心是以执行迭代为调度单位：每轮重新决定 Batch 成员，完成的请求退出，满足准入条件的请求加入。** 请求进入后，不需要等同批次其他请求全部结束才能退出；新请求也不需要等待整批结束。[Orca 的 iteration-level scheduling](https://www.usenix.org/conference/osdi22/presentation/yu) 是理解这一机制的经典入口。

```text
第 1 轮：[A, B, C] --> C 结束
轮次间：移出 C，检查 D 是否就绪且资源足够
第 2 轮：[A, B, D] --> A 结束
第 3 轮：[B, D]    --> 继续生成
```

**读图说明：** “连续”描述批次成员随请求进度持续更新。在这里，新成员加入发生在调度轮次之间，不是向一个已经启动的 GPU Kernel 中途插入请求。系统可以异步接收新请求，但仍需在后续可用的执行机会中安排它。

| 方式 | 组批和换成员的时机 | 对 LLM 多轮生成的影响 |
| --- | --- | --- |
| 固定成员的静态批处理 | 先选一批请求，直到整批完成才换成员 | 短请求结束后，容量可能闲置；新请求等待整批结束 |
| 请求级动态组批 | 根据到达情况或等待窗口组建一批请求 | 如果执行期间仍固定成员，依然存在上述问题 |
| Continuous Batching | 每轮执行前根据最新状态重新组批 | 及时移出完成请求，持续接纳符合条件的请求 |

**读表说明：** 不同系统对 Dynamic Batching 的命名可能不同。判断是否具有连续批处理能力，重点看它能否在一个长请求生成期间，跨迭代更换批次成员。

## 2 · 未做 PD 分离：同一实例内连续组批

Prefill 与 Decode 共用模型实例时，新请求要先处理 Prompt，已有请求则需要继续逐 Token 生成。调度器每轮根据计算预算、请求名额和 KV 容量安排它们。

```text
新请求 --> 等待接纳 --> 获准 Prefill --> 继续 Decode --> 结束并释放引用
                         ^                 |
                         |                 v
                    每轮重新选择请求、计算量与缓存块
```

有两种常见的执行组织方式：

- **分开执行两种阶段：** 某轮执行 Prefill，另一轮执行 Decode，在后续轮次移出结束请求、加入完成 Prefill 的请求。
- **混合执行两种阶段：** 一轮同时包含若干 Decode 和新请求的 Prefill 分块。调度器用每条请求的 Token 计算量统一安排两种阶段。

例如每轮 Token 预算为 8，A、B 正在 Decode，C 有一个长 Prompt：

```text
本轮分配：A Decode 1 + B Decode 1 + C Prefill 6 = 8 个输入 Token
执行反馈：更新 A、B 的输出和 C 的 Prefill 进度
下一轮：移出已结束请求，重新分配预算，必要时接纳新请求
```

**读图说明：** C 本轮计算 6 个 Prompt Token，不代表生成 6 个输出 Token。只有 Prompt 处理完成后，才可采样首个输出 Token。连续批处理负责动态换成员，Chunked Prefill 负责拆分 Prompt；两者可以配合。

同实例的主要矛盾是长 Prefill 可能延长执行轮次，使已有 Decode 请求的输出间隔变大。分块可以缓解干扰，但仍需要权衡新请求的 TTFT 和已有请求的 ITL。更完整的预算与队列行为见 [01 · Scheduler](01-Scheduler.md)，分块机制见 [05 · Chunked Prefill](05-Chunked-Prefill.md)。

## 3 · PD 分离：两个计算阶段，各自调度

PD 分离将 Prefill 与 Decode 放到不同模型实例或资源池。对同一请求，两个阶段通过 KV Cache 和必要的请求状态连接。

```mermaid
flowchart LR
    U[客户端请求] --> R[路由 / Proxy]
    R --> PQ[Prefill 等待队列]
    PQ --> P[Prefill 实例：处理 Prompt]
    P --> X[KV 传输与状态交接]
    X --> W[Decode 侧等待 KV / 等待资源]
    W --> D[Decode 实例：连续批处理]
    D --> O[流式输出与结束清理]
```

**读图说明：** 图中展示请求的依赖关系。工程上，Decode 请求可以提前创建并预分配接收块，KV 传输也可以与其他请求的计算重叠；不要求各框对应的操作严格串行执行。一个“实例”也可能由多张 GPU 通过 TP / PP 组成。

| 位置 | 负责什么 | 调度关注点 |
| --- | --- | --- |
| 路由 / Proxy | 选择 P、D 实例，关联两侧请求，转发输出 | P、D 负载、KV 传输路径、请求完成与取消 |
| Prefill 侧 | 处理 Prompt，建立可交接的 KV | Prompt Token 预算、计算量、缓存容量、TTFT |
| KV 传输层 | 将有效 KV 放到 D 侧可访问的位置，报告完成情况 | 带宽、块映射、异步完成、源块生命周期 |
| Decode 侧 | 使用历史 KV 持续生成，按轮次更换 Batch 成员 | 请求名额、KV 增长、单轮时长、ITL / TPOT |

两侧通常都持有可执行各自阶段的模型权重。交接时主要移动请求相关的 KV 与元数据，不需要为每个请求传输整套模型权重。

PD 分离使两种计算可以独立配置资源与并行策略，并减少长 Prefill 对 Decode 的直接干扰；这是 [vLLM 官方 PD 分离说明](https://docs.vllm.ai/en/latest/features/disagg_prefill/) 强调的主要动机。**PD 分离本身不保证原始吞吐增加**，还会引入传输、排队和资源配置成本。[DistServe](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin) 进一步研究了如何结合带宽、两阶段资源分配和延迟约束，提高满足 TTFT / TPOT 要求的有效服务能力。

### Prefill 侧也需要组批

Prefill 实例可以把多条 Prompt 组成 Batch，并在后续执行中接纳新请求。若开启 Chunked Prefill，一个长 Prompt 可以跨多轮计算，每轮重新选择请求和分块大小；若不分块，一个 Prompt 也可能在一次前向中处理完成。

```text
P 侧第 1 轮：C 的 Prompt 分块 + D 的 Prompt
P 侧第 2 轮：C 的剩余分块 + 新请求 E 的 Prompt

D 侧同时运行自己的迭代：[A, B] --> [A, B] --> ...
```

**读图说明：** P 和 D 的轮次独立推进，时长也可以不同。P 的第 2 轮不需要与 D 的第 2 轮对齐。后文重点讨论 D 侧逐 Token 的连续批处理。

## 4 · 加入 Decode Batch 前，必须完成哪些交接？

一条新请求从 P 侧完成到 D 侧首次执行，至少涉及三件事：**计算完成、依赖数据就绪、资源允许执行。** 三者发生的时刻可以不同。

```text
等待 Prefill --> 处理 Prompt --> Prefill 完成
                                   |
                                   v
                              KV 传输中
                                   |
                                   v
                         必需 KV 与请求状态就绪
                                   |
                    请求名额、预算、KV 增长空间允许
                                   |
                                   v
                          加入 Decode 批次
                                   |
                                   v
                            结束并清理资源
```

**读图说明：** 数据就绪表示请求已经具备继续计算的条件，但它仍需通过资源准入检查。D 侧满载时，KV 已经接收完成的请求也可能继续等待。调度器需要分别记录“等待依赖”和“等待执行资源”，才能判断下一步该推进什么。

### 4.1 · 交接的不只是 Token ID

| 信息 | 为什么需要 |
| --- | --- |
| 有效历史 KV 与覆盖的 Token 范围 | D 侧下一次 Attention 需要读取这些上下文 |
| Prompt、已有输出与计算进度 | 确定下一个输入 Token、位置及需要补算的范围 |
| 源 / 目标缓存块映射或访问句柄 | 定位数据并使其对应 D 侧自己的缓存布局 |
| 请求身份、采样参数与停止条件 | 关联同一请求，正确继续采样、计数和结束 |

P、D 两侧物理块编号通常不同，接收侧需要建立自己的缓存位置映射，将每段逻辑上下文对应到可访问的数据；两侧模型、适配器和 KV 表示必须兼容，TP 分片或布局不同时，需要传输实现支持相应转换。

KV 可以由 P 主动推送，也可以由 D 主动拉取，还可以经过外部缓存层。无论采用哪种路径，**发起传输不等于数据已经可用于 Attention**。需要等待消费范围对应的数据完成，并满足设备上的可见性和同步条件。

### 4.2 · 首个 Token 和第一次 Decode 的关系

先按“P 侧采样首个 Token，D 侧从它继续生成”的方式理解。设 Prompt 长度为 `S`，首个输出为 `y1`：

```text
P 侧：前向处理 x1 ... xS
      得到 Prompt 的 KV，使用最后位置 logits 采样 y1

交接：Prompt 的 KV + y1 + 请求进度和参数

D 侧第一次 Decode：输入 y1，位置为 S（从 0 开始计数）
                   读取 Prompt KV，写入 y1 的 KV，采样 y2

D 侧第二次 Decode：输入 y2，写入 y2 的 KV，采样 y3
```

**读图说明：** `y1` 被采样出来时，它自己的 KV 尚未计算。D 侧第一次 Decode 是“计算 y1，生成 y2”。这是判断交接进度有没有错一位的关键。

也有实现只交接 Prompt KV，由 D 侧补算最后一个 Prompt Token 来取得 logits，再采样首个 Token；未传输的尾部块还可能需要额外补算。原因是 KV 保存了 Attention 所需的历史状态，却不一定保留采样下一 Token 所需的输出分布。即使历史 KV 完整，也可能需要重新计算最后一个位置来取得采样结果。**因此，D 侧首次执行是否纯粹是一个 Decode Token，要看交接协议和实际缓存覆盖范围。**

首 Token 由哪侧采样、何时发给客户端，以及 D 侧如何继续计数，必须由协议约定。后面的手工推演采用 P 侧首 Token 已交付、D 侧从 `y1` 继续的方式。

### 4.3 · P 侧完成后，源 KV 仍可能要保留

```text
P 侧计算完成
    |
    v
该请求退出 P 的计算批次，但源 KV 仍被传输任务引用
    |
    v
确认传输不再依赖源块
    |
    v
释放 P 侧请求的缓存引用，允许块被回收或复用
```

**读图说明：** “不再参与计算”和“缓存可以回收”是不同事件。若源块在传输完成前被覆盖，D 侧可能收到错误数据。因此，发送侧需要在传输确认不再依赖源块后释放引用；接收侧需要在必需数据就绪后，才允许请求参与计算。启用 Prefix Cache 时，释放请求引用也不一定立即清除缓存内容。

## 5 · Decode 侧如何进行连续批处理？

D 侧每轮执行前，根据上一轮反馈和新到达的 KV 完成事件重新产生执行计划。

```text
上一轮输出 / KV 完成通知 / 新请求
    |
    v
更新已有请求：追加输出，检查 EOS、长度上限和取消
    |
    v
移出结束请求，按生命周期规则释放缓存引用
    |
    v
确认等待请求的 KV 与必要状态是否就绪
    |
    v
为已有请求检查本轮预算与新增 KV 空间
    |
    v
有剩余资源时接纳就绪请求
    |
    v
组织输入 Token、位置、上下文长度和缓存位置映射
    |
    v
运行本轮前向与采样 --> 返回反馈，准备下一轮
```

**读图说明：** 这是同步执行下的概念闭环。等待 C 的 KV 时，已就绪的 A、B 可以继续运行；应避免让一个数据尚未就绪的请求阻塞所有可执行请求。调度器可以暂时跳过依赖未满足的请求，继续安排已经就绪的工作。

### 5.1 · 同一 Batch 的请求不必处于同一生成位置

假设 A、B 已分别生成多个 Token，C 刚完成交接：

| 请求 | 本轮输入 | 输入位置（从 0 开始） | 本轮前向后的 KV 长度 |
| --- | --- | --- | --- |
| A | 最近生成的 Token | 127 | 128 |
| B | 最近生成的 Token | 511 | 512 |
| C | P 侧产生的首个输出 Token | 63 | 64 |

每条请求分别使用自己的历史上下文和缓存位置映射。

**读图说明：** 三条请求每条只处理一个新位置，但历史长度不同。执行器将输入组织到同一轮计算中，Attention 依据各自的上下文长度和缓存映射访问历史。C 不需要“追上”A、B 的生成步数才能加入。

以 Paged KV Cache 实现时，已有上下文分散在各请求的缓存块中，新请求加入主要需要建立和更新输入元数据及块映射，不需要把所有历史 KV 拼成一段连续大数组。分页缓存为动态并发提供高效的资源管理，但连续批处理这一调度思想不依赖某一种具体缓存布局。

### 5.2 · 三类资源约束仍然存在

| 约束 | 纯 Decode 时的直观含义 | 常见误解 |
| --- | --- | --- |
| 请求数上限 | 最多允许多少条活跃请求 | 空出一个名额就一定能加入新请求 |
| 每轮 Token 预算 | 普通 Decode 每个选中请求一般消耗 1 个输入 Token | 预算充足就可以忽略上下文显存 |
| KV Cache 容量 | 保存已有上下文、接收远端 KV，并支持后续增长 | Prefill 已完成，Decode 就不再增加缓存 |

例如 D 侧最多运行 4 条请求，当前只有 A、B、C 三条，但新请求 D 的 Prompt 很长，接收块无法分配。此时请求名额有空余，D 仍不能加入。反过来，KV 已接收也可能因计算预算或请求数上限继续等待。

传输中的请求还可能已经预留 D 侧缓存块。因此，**当前 Decode Batch 的大小不能代表全部 KV 占用**，需要同时观察活跃生成、等待准入和传输中的请求。

一轮组批可以按以下关系理解：

```text
处理上一轮输出与传输完成反馈
    --> 移出结束请求，释放可安全回收的资源
    --> 为已有可执行请求安排本轮计算
    --> 用剩余预算、名额和 KV 容量接纳就绪请求
    --> 各请求按自己的进度执行
    --> 反馈结果，下一轮重新组批
```

一轮只推进请求的部分生成工作。若已有请求因 KV 不足被抢占，恢复时可能需要重新获取远端 KV 或重算上下文，具体取决于系统设计。D 侧在理想稳态主要执行 Decode，尾部补算和故障恢复仍可能带来 Prefill 类工作。

## 6 · 手工推演：完成一个，就补入一个

假设 D 侧最多运行 3 条请求，每轮 Token 预算不少于 3，KV 容量足够。A、B、C 的首 Token 已由 P 侧产生并交付，还分别需要 **2、4、1 次 Decode 迭代**才能完成。新请求 D 的首 Token 同样由 P 侧交付，还需要 3 次 Decode，且在第 1 轮执行后 KV 与必要状态就绪。

| 轮次 | 本轮 Batch | 执行后剩余 Decode 次数 | 轮次间的变化 |
| --- | --- | --- | --- |
| 第 1 轮 | A、B、C | A: 1，B: 3，C: 0 | C 结束退出；D 就绪并获得准入 |
| 第 2 轮 | A、B、D | A: 0，B: 2，D: 2 | A 结束退出 |
| 第 3 轮 | B、D | B: 1，D: 1 | 没有更多就绪请求，按 2 条执行 |
| 第 4 轮 | B、D | B: 0，D: 0 | 全部结束 |

**读表说明：** D 在 B 尚未完成时就加入，B 保持自己的生成进度，无需重新 Prefill。没有更多请求时，也不必等待 Batch 填满才能执行。

若采用固定成员的静态批处理：

```text
轮次：    1      2      3      4      5      6      7
批次： [A,B,C] [A,B,-] [-,B,-] [-,B,-] [D,-,-] [D,-,-] [D,-,-]
                                     ^
                              首批全部完成，D 才能进入
```

**读图说明：** `-` 表示无法用于新请求的执行容量，不意味着系统一定对空位置实际做无用计算。静态批处理要 7 个迭代轮次；连续批处理只需 4 个轮次，D 的等待也更短。

两者有效请求步数都为 `2 + 4 + 1 + 3 = 10`。如果只按“每轮最多 3 个请求执行机会”计数，静态方式使用了 `10 / (7 × 3) ≈ 48%`，连续方式使用了 `10 / (4 × 3) ≈ 83%`。

这只是执行机会的示意比例，不能当作真实 GPU 利用率或加速比。Batch 大小、上下文长度和调度开销都会改变每轮耗时，真实性能需要测量。

再修改一个条件：**D 的 KV 到第 2 轮后才就绪。** 即使 C 在第 1 轮后结束，D 也不能马上加入；第 2 轮只能运行 A、B。这说明连续批处理可以利用就绪工作，却不能消除数据依赖造成的等待。

## 7 · 为什么有收益，又为什么不能无限加大 Batch？

### 7.1 · 多条请求共同提高单轮计算效率

在普通 Decode 中，一条请求本轮只输入一个 Token。把多条请求放到同一轮，可以形成更大的矩阵运算，提高并行度，并让一次权重访问服务更多 Token；不同请求的历史 KV 仍然需要分别访问。

连续批处理还通过及时补入请求，减少长短输出混合造成的空闲执行容量。这两种收益分别来自“同轮组批”和“跨轮更新成员”。

若本轮有 `b` 条请求，每条得到一个输出 Token，则近似有：

```text
输出吞吐 ≈ b / T_step(b, 上下文长度分布)
```

**公式说明：** `T_step` 是这轮执行所需时间。增大 `b` 往往能提高吞吐，但也可能增加单轮时长，使各请求的输出间隔变大。长上下文带来的 KV 读取量也会影响它，所以不能仅用 Batch 大小预测速度。

### 7.2 · 接收和保留 KV 都有成本

对采用普通全上下文 Attention 的模型，忽略块填充、共享前缀、量化元数据和并行复制，单条长度为 `S` 的历史 KV 大小约为：

```text
M_KV ≈ 2 × L × S × H_kv × D_head × bytes_per_element
```

其中 `2` 代表 K 和 V，`L` 是层数，`H_kv` 是 KV Head 数，`D_head` 是 Head 维度。GQA / MQA 应使用 KV Head 数，而不是 Query Head 数。

例如 `L=32、H_kv=8、D_head=128、FP16/BF16 每元素 2 字节`：

```text
每 Token 的 KV ≈ 128 KiB
8192 个 Token 的 KV ≈ 1 GiB
```

**读公式说明：** 这里估算全模型逻辑 KV 总量，不是每个 TP Rank 都保存 1 GiB。实际每卡存储和跨网络传输量还取决于分片、复制、缓存命中及 传输时的缓存布局。这个量级说明长 Prompt 的交接成本不能忽略。

简化的传输耗时可估为 `T_transfer ≈ 实际传输字节数 / 有效带宽 + 协议与同步开销`。传输可与其他请求的 Decode 重叠，但新请求仍需等待自己的必要 KV 就绪。

### 7.3 · 两侧速率失衡会形成积压

如果 P 持续完成新请求，而 D 侧已有请求生成很长，D 的请求名额和 KV 迟迟不释放，那么完成 Prefill 的请求会在交接或准入阶段积压。等待传输还可能让 P 侧源块长期占用。

系统因此需要结合 D 侧负载进行路由、准入或背压：控制进入 P 的工作量、限制传输中请求数、为长请求预估 KV 增长，必要时调整 P / D 资源比例。连续批处理解决单个执行实例的批次更新；两阶段容量协调决定系统能否持续稳定地接纳请求。

## 8 · 观察哪些指标？

| 指标 | 观察什么 | 帮助定位的问题 |
| --- | --- | --- |
| TTFT | 从请求到达到首 Token 实际交付的时间 | P 排队、Prompt 计算、交接路径上的等待 |
| ITL / TPOT | 相邻输出的间隔 / 后续输出的平均耗时 | D 单轮变慢、请求被跳过、交接处卡顿 |
| 实际 Decode Batch 大小 | 每轮执行了多少条请求 | 是否能持续补入请求，是否缺少就绪工作 |
| P / D 等待队列与传输中请求数 | 各阶段积压在哪里 | P、网络、D 的能力是否匹配 |
| KV 占用与抢占次数 | 活跃、待准入、传输保留的缓存 | 显存限制是否导致排队、恢复或反复抢占 |
| 输出 Token/s 与满足 SLO（服务延迟目标）的完成率 | 产出量及其延迟是否合格 | 吞吐提升是否伴随不可接受的等待 |

**读表说明：** 首 Token 的交付路径决定 TTFT 应包含哪些阶段。如果 P 产生的 `y1` 立即发给客户端，随后 KV 传输和 D 准入等待可能主要表现为 `y1 → y2` 的长间隔；若首 Token 要等 D 就绪后才交付，这些等待会进入 TTFT。看流畅性时，还应观察 ITL 的 P95 / P99，平均 TPOT 可能掩盖偶发停顿。

“Batch 总是很大”也不能单独证明调度好：很大的 Batch 可能带来更长轮次、更高显存压力和更差的尾部延迟。需要结合吞吐、延迟与排队一起判断。

## 9 · 连续批处理成立的机制基础

连续批处理依赖的不只是动态改变 Batch 大小，还需要引擎能够独立维护每条请求的状态。

| 机制基础 | 为什么需要 |
| --- | --- |
| 请求进度独立保存 | 移出、加入其他请求时，已有请求仍能从自己的位置继续 |
| 每轮重新生成执行计划 | 根据完成、到达和数据就绪事件及时调整成员 |
| 上下文按请求定位 | 不同长度、不同生成步数的请求可以共用一轮计算 |
| 数据就绪与资源准入分开判断 | 避免在 KV 尚不可用时执行，也避免将“已接收”误认为“可立即运行” |
| 计算生命周期与缓存生命周期分开管理 | 请求退出计算批次后，仍能安全完成传输，再回收缓存 |

以 PD 分离中的一条新请求为例，关键依赖链是：

```text
确认可交接的上下文范围
    --> 为接收数据准备缓存空间
    --> 传输 KV，期间已有 Decode 请求继续推进
    --> 确认接收完成及有效上下文范围
    --> 必要时补算未覆盖的尾部或取得采样结果
    --> 通过资源准入检查，加入后续执行轮次
```

**读图说明：** 缓存空间已分配、传输已发起和 KV 已可用于计算，是三个不同的时刻。若传输不完整，系统需要重新确认有效上下文，并通过重传或补算满足依赖。连续批处理利用已就绪的工作持续推进，PD 分离则让这些工作在不同计算资源间完成交接。
