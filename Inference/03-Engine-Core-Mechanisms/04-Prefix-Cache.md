# 04 · Prefix Cache

理解引擎如何识别已经计算过的公共前缀，复用对应 KV，并在共享、请求结束和缓存淘汰之间管理数据生命周期。

**阅读范围：** 从 vLLM V1 的设计思路出发，按普通文本生成、因果 Attention、相同模型执行条件理解机制。示例采用完整块复用，前缀识别粒度与物理块大小相同；更细粒度匹配、多模态及混合缓存布局不在本篇展开。

前置知识：[Paged KV Cache](03-Paged-KV-Cache.md)、[Scheduler](01-Scheduler.md)。

## 1 · 为什么公共前缀能够复用？

很多请求包含相同的系统指令、工具说明或文档开头。如果每条请求都重新计算这部分 Prompt，会重复建立相同的历史 KV。

因果 Attention 中，一个位置只能依赖它自己及之前的位置。在模型和执行条件一致时，两条请求相同的前缀可以得到可复用的 KV；后续输入不同，不会改变前缀已经建立的状态。

```text
请求 A：[共同前缀] + [问题 A]
请求 B：[共同前缀] + [问题 B]
             |
             v
只建立一份可复用的前缀 KV
A、B 分别计算自己的后缀，并继续生成
```

**读图说明：** Prefix Cache 复用的是输入上下文的计算结果。即使共享前缀，两个请求仍会根据自己的后缀、采样参数和生成过程独立输出。

它主要减少重复 Prefill 工作。Decode 仍需读取共享前缀的 KV，每条请求的后续输出也仍需继续计算。

## 2 · “相同”必须包含完整前缀上下文

仅仅当前块的 Token 相同，不足以共享 KV，因为这一块还依赖之前的上下文。

```text
请求 A：[a b c d] [e f g h]
请求 B：[w x y z] [e f g h]

第二块的 Token 相同，但之前的上下文不同。
第二块的 KV 通常不同，不能直接复用。
```

识别前缀时，必须把当前内容与之前的历史一起考虑。一个常见思想是逐块形成链式指纹：

```text
第 0 块身份：首块 Token + 影响计算的执行条件
第 1 块身份：第 0 块的前缀身份 + 当前块 Token + 执行条件
第 2 块身份：第 1 块的前缀身份 + 当前块 Token + 执行条件
```

**读图说明：** 前一块的身份已经包含更早的历史，因此链式指纹描述的是“截至当前块的前缀”。查找时用指纹定位候选缓存，并依赖可靠的身份校验避免错误复用；不能把一个容易碰撞的摘要当成内容必然一致的证明。

| 条件 | 对复用的影响 |
| --- | --- |
| 相同的 Token 序列与位置语义 | 相同文字经过不同模板或分词后，未必构成相同前缀 |
| 相同的模型与适配器 | 不同权重产生的 KV 通常不能混用 |
| 兼容的 KV 表示与执行布局 | 跨实例复用时还需保证布局可直接使用或能够正确转换 |
| 缓存隔离条件一致 | 不同缓存命名空间或隔离标识可以限制共享范围 |
| 对应 KV 已计算完成且仍有效 | 只识别到 Token 内容，不代表数据已经可用 |

采样温度等只影响后续采样的参数，通常不会改变固定 Prompt 的 KV。是否可复用应围绕“哪些条件会改变上下文计算结果”判断。

## 3 · 为什么通常按完整块复用？

完整块的内容边界固定，计算完成后可作为稳定的共享单元。未填满的尾块仍可能继续写入，直接共享它会让不同请求的后续写入互相影响。

```text
每块 4 个 Token，公共前缀长 10：

[a b c d] [e f g h] [i j ... ...]
   完整块     完整块      未满尾块
     |          |             |
   可复用     可复用     本篇示例重新计算
```

**读图说明：** 虽然公共前缀有 10 个 Token，在这个完整块方案中，通常只能直接复用前 8 个。剩余 2 个会与请求自己的后缀一起计算。公共文本长度与实际跳过的计算长度可能不同。

共享块应保持只读。各请求的差异部分使用自己的可写空间；如果某种方案允许共享未满尾块，继续写入前就需要分离可写副本，或者采用其他保证写入安全的方式。

完整块复用避免了常规路径上的共享尾块写入问题。这里的块边界是教学假设，实际系统也可以使用更细的匹配粒度和不同的物理块布局。

## 4 · 查找命中后，如何减少 Prefill？

```text
新请求到达
    |
    v
从开头检查连续前缀对应的有效缓存
    |
    v
确定可复用的前缀范围
    |
    v
引用命中块，建立本请求的缓存映射
    |
    v
检查后缀计算所需的预算与新增缓存空间
    |
    v
只计算尚未建立上下文的部分
    |
    v
新完整块计算完成，成为后续请求的复用候选
```

**读图说明：** 命中前缀既改变计算起点，也改变空间分配需求。引用正在被其他请求使用的块，不需要再复制一份相同数据；引用无人使用但仍保留内容的块，则会让这块重新受到保护，不能再被覆盖。

本篇的全上下文模型中，复用的是从开头连续可用的前缀。某个中间块缺失时，后面孤立保留的块不足以直接构成完整上下文，示例会从缺失处重新计算。

### 即使 Prompt 完全相同，也可能需要末尾计算

KV 保存了 Attention 所需的历史状态，但不一定保存采样首个输出 Token 所需的输出分布。若缓存只有 KV，引擎仍可能需要重新计算 Prompt 的最后位置来取得采样结果。

如果调度和复用以完整块为粒度，这个要求还可能使最后一整块参与重算。

因此，需要区分：

| 概念 | 含义 |
| --- | --- |
| 内容相同 | 输入前缀可以对应相同计算结果 |
| 数据命中 | 对应 KV 仍在缓存中，且可用 |
| 实际跳过计算 | 本轮真正不需要重新前向的 Token 范围 |

**读表说明：** 不能仅凭“Prompt 完全命中”就推断 TTFT 为零。排队、准入、末尾计算和采样仍可能产生延迟。

## 5 · 手工推演：共享前缀与一次修改

假设每块容纳 4 个 Token，不存在末尾采样补算对本例命中边界的额外影响。A 已计算完成以下 12 个 Prompt Token，前三块仍在缓存中：

```text
A：[a b c d] [e f g h] [i j k l]
       P0        P1        P2
```

B 的 Prompt 为 14 个 Token：

```text
B：[a b c d] [e f g h] [i j m n] [o p]
```

| 检查范围 | 是否复用 A 的块 | 原因 |
| --- | --- | --- |
| 位置 0–3 | 是，引用 P0 | 首块及执行条件相同 |
| 位置 4–7 | 是，引用 P1 | 当前块与此前历史都相同 |
| 位置 8–11 | 否 | 当前块出现差异 |
| 位置 12–13 | 否 | 属于 B 的后续内容，且尾块未满 |

**读表说明：** A、B 的逐 Token 公共前缀长 10，但完整块复用跳过 8 个 Token。B 还需计算 6 个输入 Token，使用自己的后缀块；它不会覆盖 A 的 P2。

在这个简化模型中，两条请求的完整 Prompt 分别需要 3 块与 4 块。若独立保存，共需 7 块；共享前两块后，共需 5 块，即 2 个共享块、A 的 1 个私有块、B 的 2 个私有块。

再将 B 的第一个块改为 `[a b X d]`，其余 Token 保持不变：

```text
B'：[a b X d] [e f g h] [i j m n] [o p]
```

第一个块已不相同，后面的块虽然局部内容可能一致，前缀身份也都改变了。按完整块匹配，B' 无法复用 A 的块，需要计算全部 14 个 Prompt Token。

如果修改发生在第二块，第一块仍可复用；如果修改发生在尚未复用的后缀，前两块的命中不受影响。

## 6 · 共享、释放与淘汰如何配合？

```text
A 使用 P0：使用者数量为 1
B 命中 P0：使用者数量变为 2
A 结束：  数量降为 1，B 仍在使用，不能覆盖
B 结束：  数量降为 0，可保留内容，也可重新分配
C 命中：  若尚未覆盖，重新保护该块并复用
新数据覆盖：先取消旧缓存身份，再写入新内容
```

**读图说明：** 引用计数描述当前有多少使用者；缓存索引描述块中仍保存了哪个可复用前缀。两者承担不同职责，所以引用归零不必立即删除缓存内容。

容量紧张时，可以淘汰无人依赖的缓存块，将空间交给新的请求。近期复用情况、释放顺序和前缀价值都可能影响淘汰选择；具体策略可以不同，但不能覆盖仍被活跃请求或传输任务依赖的数据。

淘汰一个块的身份后，需要保证后续请求不会再把它误认为有效命中。已存在的其他前缀缓存也不保证一直可用，新请求必须重新确认完整可复用范围。

### 抢占后保留文本，不等于保留全部 KV

请求被抢占后，Prompt 和已生成 Token 可以保留，但原来的 KV 引用会解除。恢复时，仍存活的前缀缓存可以减少重算；已被淘汰的部分则必须重新建立。

如果某个块还被其他请求共享，它会继续保留。因此，抢占一条请求释放的实际空间，可能小于该请求逻辑上下文对应的块数。

## 7 · 哪些负载更容易受益？

| 负载特点 | 预期效果与限制 |
| --- | --- |
| 很多请求共享长系统指令或工具定义 | 有较多重复 Prefill 工作可省去 |
| 同一文档被反复提问 | 文档放在相同前缀位置时，更容易复用 |
| 多轮对话持续追加内容 | 历史前缀仍在缓存且格式稳定时，可复用更多上下文 |
| 共享内容前插入不同时间戳或请求标识 | 前缀较早出现差异，后续大段相同文字也可能无法复用 |
| 请求间隔很长或缓存容量不足 | 热门前缀可能在下次请求前被淘汰 |
| Prompt 很短、输出很长 | 可省 Prefill 较少，整体耗时可能仍由 Decode 主导 |

Prefix Cache 改善的是重复工作。请求数上限、后缀缓存空间和 Decode 带宽仍会限制准入与吞吐；高命中率不意味着所有请求都能立即运行。

PD 分离时，还需区分命中发生在哪一侧。P 侧命中可减少 Prompt 计算，但若 D 侧没有相应 KV，交接仍可能需要传输；只有接收侧已经持有兼容数据，才有机会同时减少传输量。

## 8 · 观察哪些指标？

| 指标 | 观察什么 | 帮助定位的问题 |
| --- | --- | --- |
| 请求命中比例 | 有多少请求至少复用了一部分前缀 | 工作负载是否有重复输入 |
| 实际复用 Token 比例 | 真正跳过多少 Prompt Token 的计算 | 命中是否只覆盖很短前缀 |
| Prefill 计算量与 TTFT | 减少的计算是否转化为首 Token 改善 | 排队或末尾计算是否仍占主要时间 |
| 共享物理块数与引用数量 | 多条请求是否共享同一份存储 | 是否实际节省活跃 KV 容量 |
| 淘汰与重新计算量 | 有用前缀是否频繁被覆盖 | 缓存容量、路由或复用间隔是否合适 |
| Decode 吞吐与 ITL / TPOT | 后续生成成本有没有变化 | 是否错误地把 Prefill 收益推广到全程 |

**读表说明：** 命中率必须说明分母：按请求、按查找块还是按 Token 统计，含义不同。评估收益时，应同时记录实际跳过的计算量与用户感知延迟。
