# 05 · Chunked Prefill

理解长 Prompt 如何拆成多轮计算，分块之间如何保留上下文，以及 Prefill 与 Decode 如何共享执行预算。

**阅读范围：** 从 vLLM V1 的设计思路出发，按普通自回归生成、因果全上下文 Attention、同步执行理解机制。主要讨论 Prefill 与 Decode 共用实例的情况，第 7 节补充 PD 分离。推演不包含推测解码、多模态与异步流水线。

前置知识：[Scheduler](01-Scheduler.md)、[Continuous Batching](02-Continuous-Batching.md)、[Paged KV Cache](03-Paged-KV-Cache.md)、[Prefix Cache](04-Prefix-Cache.md)。

## 1 · 为什么要拆分长 Prompt？

新请求要先处理 Prompt，才能生成首个输出 Token。已有 Decode 请求则希望每隔较短时间推进一步，持续向用户输出。

如果一个很长的 Prompt 在一轮里整体处理，这轮计算可能持续较长时间。同实例中的 Decode 请求即使也参与了这轮，输出通常仍需等待本轮完成；如果两阶段分开执行，Decode 还可能等待完整 Prefill 轮次结束。

**Chunked Prefill 的核心是：将一个 Prompt 的待计算部分拆到多个执行轮次，每轮只处理一段，保留已建立的 KV，让其他请求在后续调度机会中继续推进。**

```text
完整 Prefill： [一次处理全部长 Prompt] --> 首个输出 Token

分块 Prefill：[前一段] --> [中间一段] --> [最后一段] --> 首个输出 Token
                  ^            ^             ^
               每轮可以同时安排其他可执行请求
```

**读图说明：** 分块缩短单次占用计算资源的范围，增加调度机会。它不会让尚未读取完整 Prompt 的请求提前得到正式回答，也不会使 Prompt 剩余部分无需计算。

## 2 · 分块以后，模型仍然看到完整历史

分块不是把 Prompt 拆成彼此独立的问题。后一块仍需访问前面分块建立的上下文。

```text
Prompt：x1 ... x6 | x7 ... x12 | x13 ... x18

第 1 块：处理 x1–x6，保存这些位置的 KV
第 2 块：读取第 1 块的 KV，处理 x7–x12，继续追加 KV
第 3 块：读取前 12 个位置的 KV，处理 x13–x18
         根据最后位置的输出分布，采样首个输出 Token
```

**读图说明：** 每一块内部仍遵守因果关系：当前位置可以关注之前已缓存的位置和本块内更早的位置，不能访问未来位置。正确保留历史 KV、位置与 Attention 语义后，分块计算应与完整 Prefill 表达相同的上下文关系；不同计算路径可能有浮点数值差异。

| 跨轮保存的信息 | 为什么需要 |
| --- | --- |
| 已经可用的上下文范围 | 知道哪些 Prompt Token 不需要重新计算 |
| 尚未处理的 Prompt 后缀 | 确定下一轮的输入内容 |
| 绝对位置或等价的位置语义 | 后一块继续使用原 Prompt 中的位置 |
| 有效 KV 与缓存位置映射 | 后一块能够读取前面的历史 |
| 请求的采样与停止条件 | Prompt 完成后，正确进入生成阶段 |

中间分块主要推进 Prompt 的计算进度。只有处理到 Prompt 末尾，才得到用于正式生成首个输出 Token 的结果。

## 3 · 分块大小如何由预算决定？

可以把一次分配理解为同时受到三种限制：

```text
本轮 Prefill 分块大小不超过：
    该请求剩余的 Prompt Token 数
    本轮剩余的 Token 预算
    调度策略允许的单请求分块上限（若设置）

随后还要通过 KV 空间与其他准入检查。
```

**读图说明：** 总预算约束一轮所有请求的计算量，单请求上限控制一个长 Prompt 本轮最多占多少预算。两者不同；分块也不必每轮保持相同大小。

例如总预算为 8，两条 Decode 请求各处理 1 个输入 Token，长 Prompt 可以利用剩余 6 个 Token。下一轮 Decode 请求数量变为 4 时，留给 Prefill 的预算可能只有 4。

| 约束 | 对分块调度的影响 |
| --- | --- |
| 总 Token 预算 | 限制所有选中请求的输入 Token 总量 |
| 单请求分块上限 | 避免单个长 Prompt 独占大量计算预算 |
| 请求数上限 | 长 Prompt 跨轮执行期间仍可能占用活跃名额 |
| KV 容量 | 决定能否保存历史并容纳本轮新增位置 |
| 等待顺序与公平性 | 决定剩余预算交给哪个 Prefill 请求 |

相同的输入 Token 总数不代表相同执行时间。Prefill 与 Decode 的计算形态不同，历史长度、请求数量和模型结构也会影响单轮耗时；Token 预算是一种调度尺度，不能直接当作固定毫秒预算。

## 4 · 与 Decode 协作，不等于固定优先级

本篇采用这样的策略推演：先安排两条已有 Decode 请求，再将剩余预算交给一条长 Prompt；之后该 Prompt 作为已接纳请求跨轮推进。

```text
开始本轮调度
    --> 检查已有请求的待计算量与缓存条件
    --> 为两条 Decode 各分配 1 个 Token
    --> 为长 Prompt 分配剩余预算允许的一段
    --> 组成混合批次并执行
    --> 更新输出与 Prefill 进度，下一轮重新分配
```

**读图说明：** 这是明确设定的示例策略。实际调度还受等待顺序、优先级和分块上限影响；“先处理已接纳请求”也可能先处理某条尚未完成 Prefill 的请求，不能推断所有 Decode 永远先于所有 Prefill。

分块增加了协调机会，但公平性仍需要调度策略保证。如果剩余预算长期被少数请求占用，新请求仍可能排队很久；如果每轮都只处理 Prefill，已有 Decode 也仍可能出现较长输出间隔。

## 5 · 手工推演：18 个 Prompt Token 与两个 Decode

假设每轮总 Token 预算为 8，最多同时接纳 3 条请求。A、B 已完成 Prefill，每轮各处理 1 个 Decode 输入 Token，且在推演期间均不结束。C 的 Prompt 长度为 18，KV 容量足够，不使用 Prefix Cache，也不设置额外的单请求分块上限。

采用第 4 节的策略，每轮先安排 A、B，再处理 C。

| 轮次 | A 的计算量 | B 的计算量 | C 的计算量 | C 已处理的 Prompt | 执行后变化 |
| --- | --- | --- | --- | --- | --- |
| 第 1 轮 | Decode 1 | Decode 1 | Prefill 6 | 6 / 18 | C 保存前 6 个位置的 KV，尚无正式输出 |
| 第 2 轮 | Decode 1 | Decode 1 | Prefill 6 | 12 / 18 | C 读取历史，追加第 7–12 个位置的 KV |
| 第 3 轮 | Decode 1 | Decode 1 | Prefill 6 | 18 / 18 | C 完成 Prompt，采样首个输出 Token |
| 第 4 轮 | Decode 1 | Decode 1 | Decode 1 | 18 / 18 | C 计算首个输出 Token 的 KV，采样第二个输出 Token |

**读表说明：** 前三轮每轮处理 8 个输入 Token，但 C 只在第三轮得到首个输出。第四轮 C 已有 19 个 Token：18 个 Prompt 和 1 个输出；其中只有最新输出的 KV 尚未建立，所以普通 Decode 只需处理 1 个输入 Token。

### 分块边界不必等于缓存块边界

继续假设每个 KV 块容纳 4 个 Token，且仅按本轮需求分配空间：

| C 的有效 KV 长度 | 所需物理块数 | 最后一个块的使用量 |
| --- | --- | --- |
| 第 1 轮后：6 | 2 | 2 / 4 |
| 第 2 轮后：12 | 3 | 4 / 4 |
| 第 3 轮后：18 | 5 | 2 / 4 |
| 第 4 轮后：19 | 5 | 3 / 4 |

**读表说明：** Prefill 分块一次处理 6 个 Token，KV 存储块一次容纳 4 个 Token，它们是不同粒度。后一轮可以继续填充已有尾块，再分配新块；无需因为 Prefill 分块结束而浪费整个缓存块。某些执行方案可能额外要求对齐，本例没有这类约束。

### 修改一个条件：限制单请求每轮最多 Prefill 4 个 Token

A、B 仍各使用 1 个 Token，C 会按 `4 + 4 + 4 + 4 + 2` 分 5 轮完成，而不是 3 轮。若没有其他可执行请求，前几轮可以留下 2 个预算未用。

这说明“总预算还有空间”与“应该让单个长 Prompt 全部用完”是两种决策。单请求上限可以控制占用，但更小分块也可能让 C 更晚获得首 Token。

## 6 · 分块大小如何影响延迟与吞吐？

| 选择 | 可能带来的收益 | 可能付出的成本 |
| --- | --- | --- |
| 较大的 Prefill 分块 | 更快推进长 Prompt，减少轮次数与重复调度开销 | 单轮可能更长，同轮 Decode 输出间隔变大 |
| 较小的 Prefill 分块 | 更频繁地调整请求与安排 Decode | Prompt 需要更多轮，执行和历史访问开销可能增加 |
| 同轮混合 Prefill 与 Decode | 两种工作共享执行机会，减少阶段间长时间等待 | 混合比例不合适时，仍会干扰 Decode 延迟 |

**读表说明：** 这些是机制上的取舍，真实收益取决于负载与执行实现。较小分块不能直接推导出更低的 TTFT，较大分块也不能保证更高的有效吞吐。

可以把 C 的 TTFT 按时间来源理解：

```text
TTFT ≈ 首次获准执行前的排队时间
       + 各个 Prefill 分块所经历的执行时间
       + 分块之间未被安排计算的等待时间
       + 首 Token 的采样与交付开销
```

分块可能缩短其他请求的等待，却延长 C 自己完成 Prompt 的时间。如果系统中很多短请求原本排在长 Prompt 后面，分块与合适的接纳策略也可能改善它们的首 Token 延迟。

对 A、B 而言，ITL 取决于它们两次输出之间经过的实际时间。即使每轮都获准 Decode，较长的混合执行轮次也会使输出变慢；若被跳过，还要加入等待轮次的时间。

评估吞吐时，需要观察单位时间的有效输出与完成请求，而不是只比较每轮输入 Token 数。

## 7 · 与 Prefix Cache、分页缓存和 PD 分离的关系

### Prefix Cache 先减少工作，Chunked Prefill 再拆分剩余工作

若 C 的 18 个 Prompt Token 中，前 8 个已经可复用，则剩余待计算量为 10。仍按每轮留给 C 6 个 Token 的例子：

```text
引用前 8 个位置的有效 KV
第 1 轮：计算接下来的 6 个 Prompt Token，总进度达到 14
第 2 轮：计算最后 4 个 Prompt Token，得到首个输出
```

**读图说明：** 缓存命中改变计算起点，分块决定剩余工作怎样跨轮执行。这里的可复用 8 个位置已通过有效性检查，不额外涉及完整命中后的末尾采样补算。

### 分页缓存支持逐步增长，但分块不限制最终上下文大小

Chunked Prefill 每轮只计算一段，缓存可以按需求增长，从而减少一次性新增工作的规模。但全上下文 Attention 仍需要保留已经处理的历史，18 个 Prompt Token 完成后，仍需保存这 18 个位置的 KV。

因此，分块不能把总 KV 需求永远限制在一个分块大小。活跃请求过多时，即使单轮 Token 预算不大，缓存仍可能耗尽并导致抢占。

### PD 分离后，两侧轮次独立推进

P 侧仍可对长 Prompt 分块，让不同 Prefill 请求共享预算；D 侧独立运行自己的连续批处理轮次，不必等待 P 侧每个分块结束。

```text
P 侧：C 第 1 块 --> C 第 2 块与其他 Prompt --> C 最后一块
                                                   |
                                                   v
                                           KV 交接与 D 侧准入

D 侧：A、B --> A、B --> A、B --> ... --> A、B、C
```

**读图说明：** 两条时间线不要求轮次对齐。PD 分离减少了长 Prefill 对同实例 Decode 的直接干扰，但仍存在交接、资源准入与两侧负载协调问题。

有些系统可以在计算过程中逐步传输 KV，以重叠计算和通信；这不意味着 D 侧能忽略 C 尚未完成的 Prompt。正式继续生成前，仍需满足交接协议规定的计算与数据依赖。

## 8 · 被抢占后，分块进度如何恢复？

```text
长 Prompt 已处理一部分
    --> KV 空间不足，请求被抢占
    --> 保留 Prompt 和已有输出，解除缓存引用
    --> 恢复时重新确认仍然有效的上下文
    --> 复用存活前缀，重新计算缺失部分
    --> 继续处理剩余 Prompt 或继续 Decode
```

**读图说明：** 曾经计算到某个位置，不代表恢复时那个位置的 KV 仍可用。恢复依据的是当前有效数据，而不是仅凭原来的历史进度。

如果一个长 Prompt 反复只推进少量工作就被抢占，之前的分块可能多次重算。此时较高的输入计算量不一定转化为更多有效输出，应同时观察抢占与重复计算。

## 9 · 观察哪些指标？

| 指标 | 观察什么 | 帮助定位的问题 |
| --- | --- | --- |
| 分块大小与完成 Prefill 所需轮数 | 长 Prompt 怎样推进 | 分块是否过细或单请求占用过大 |
| 每轮 Prefill / Decode Token 分配 | 两类工作如何共享预算 | Decode 是否被挤压，Prefill 是否长期没有进展 |
| TTFT 及其尾部延迟 | 新请求多久得到首 Token | 排队、分块等待或长 Prompt 是否拖慢响应 |
| ITL / TPOT 及其尾部延迟 | 已有请求的输出是否流畅 | 混合轮次过长或请求被频繁跳过 |
| 输出吞吐与满足 SLO 的完成率 | 有效产出及延迟是否合格 | 分块调整是否改善了实际服务能力 |
| KV 占用、抢占与重算量 | 跨轮保留历史的成本 | 显存压力是否抵消分块收益 |

**读表说明：** 分块调整需要同时观察新请求与已有请求。平均值可能掩盖少数长 Prompt 或偶发长轮次造成的停顿，TTFT 与 ITL 的 P95 / P99 更能反映这种干扰。

## 10 · 将五种机制串成一次请求执行

| 机制 | 在请求执行中解决什么问题 |
| --- | --- |
| Scheduler | 每轮决定谁可以执行、处理多少 Token，并协调资源 |
| Continuous Batching | 在轮次之间移出完成请求、接纳满足条件的新请求 |
| Paged KV Cache | 为各请求分配、定位、扩展和回收历史上下文空间 |
| Prefix Cache | 识别可复用的公共前缀，减少重复计算与存储 |
| Chunked Prefill | 将剩余长 Prompt 分多轮处理，与其他工作共享执行机会 |

```text
新请求到达
    --> 查找有效前缀，确定剩余计算量
    --> 调度器检查名额、Token 预算与 KV 容量
    --> 为本轮 Prefill 分块建立缓存映射并执行
    --> 保存进度，后续轮次继续处理 Prompt
    --> Prompt 完成，采样首个输出 Token
    --> 每轮 Decode，根据反馈调整批次成员
    --> 结束后解除引用，缓存按共享与保留规则处理
```

**读图说明：** 五种机制分别管理选择、批次成员、物理空间、重复工作与单次工作量。理解它们的协作，需要沿着同一条请求同时追踪计算进度、缓存状态和执行机会。
